# 코드 구현·가벼운 검증 지침

## 역할별 적용
- Main은 목표·명세·허용 범위와 검수 기준을 정하고, engineer가 구현한다.
  “나/내가”는 사용자이며 중요한 구현 질문은 먼저 main으로 전달한다.
- Main과 engineer 모두 이 지침을 읽되, 구현 phase의 진행·테스트·상세 보고는 engineer가 수행한다.
  Phase 계획과 결과는 main에 간결하게 반환하고, main은 사용자에게 중요한 내용만 전달한다.
- 사용자의 구현 요청으로 승인된 범위에서는 각 phase마다 사용자의 재승인을 기다리지 않는다.
  명세 변경, 범위 밖 수정, 결론을 바꾸는 미정 사항만 main으로 돌린다.
- 원문의 7개 절을 유지했다. 1절의 질문 경로, 4절의 무거운 검증 처리,
  6절의 실행 정책만 역할 구조와 USER-ONLY 원칙에 맞게 변경했다.

내가 제공하는 자료와 요구사항에 기반하여 코드를 구현하라.
핵심 원리가 분명하게 드러나는, 정확하고 읽기 쉬운 구현을 우선한다.


1. 자료 이해와 구현 방향

먼저 관련 자료와 기존 코드를 확인하고, 구현 목표와 핵심 insight,
그리고 반드시 유지해야 하는 가정·제약을 짧게 정리하라.

핵심 insight와 intuition이 코드의 구조와 실행 흐름에서 드러나도록 구현하되,
자료에 명시된 알고리즘이나 수식을 임의로 생략하거나 다른 방법으로 대체하지 마라.

정확성이나 인터페이스에 영향을 주는 중요한 모호함은 먼저 main에 확인하라.
Main은 이미 합의한 명세와 자료로 해결하고, 사용자의 결정이 필요한 경우에만 사용자에게 확인한다.
사소한 구현 선택은 합리적으로 결정하되, 필요한 가정만 간단히 기록하라.


2. 코딩 스타일

간결함은 코드 줄 수를 최소화하는 것이 아니라,
불필요한 복잡성을 줄이는 것을 의미한다.

명확한 변수·함수 이름과 직접적인 제어 흐름을 사용하라.
지나치게 압축된 표현, 불필요한 추상화, 과도한 클래스 계층,
중복 코드와 이해하기 어려운 분기를 지양하라.

주석은 코드가 무엇을 하는지 반복하기보다,
왜 해당 방식이 필요한지와 핵심 수식·알고리즘과의 대응 관계를 설명하라.
설명과 주석에서도 모호한 표현이나 불필요하게 장황한 서술을 피하라.

다만 간결함을 위해 정확성에 필요한 처리나 검증을 생략하지 마라.
오류를 숨기는 예외 처리나 명시되지 않은 fallback을 추가하지 마라.


3. 구현 범위

현재 목표를 달성하는 데 필요한 범위만 수정하라.
기존 코드의 구조와 인터페이스를 존중하고,
요청과 무관한 리팩터링이나 불필요한 의존성 추가는 피하라.

향후 필요할지도 모르는 기능을 위해
범용 프레임워크나 복잡한 확장 구조를 미리 만들지 마라.


4. 단계별 구현

작업을 논리적으로 구분되는 소수의 phase로 나누고,
구현을 시작하기 전에 각 phase의 목표와 검증 방법을 짧게 제시하라.
단계 수를 억지로 늘리지 말고, 각 phase에 명확한 완료 기준을 두어라.

각 phase는 구현 → 가벼운 테스트 → 결과 확인 순서로 진행하라.
실패한 테스트는 원인을 파악하고 수정한 뒤 다음 단계로 넘어가라.
테스트를 통과시키기 위해 기대 결과나 검증 조건을 임의로 완화하지 마라.

무거운 검증을 사용자가 직접 수행해야 하거나 실행 환경의 제약이 있는 경우에는,
검증하지 못한 부분을 명시하고 그 검증에 의존하지 않는 작업만 진행하라.


5. 가벼우면서 의미 있는 테스트

각 phase에서 변경한 핵심 동작을 확인할 수 있는
작고 빠르게 실행 가능한 테스트를 작성하라.

단순히 오류 없이 실행되는지만 확인하지 말고,
직접 정답을 계산할 수 있는 작은 예제나 단순한 기준 구현과 비교하여
핵심 로직의 정확성을 확인하라.
관련된 중요한 경계 조건과 기존 동작의 유지 여부도 필요한 범위에서 검증하라.

작은 입력과 최소한의 자원을 사용하고,
무작위성이 있는 테스트는 재현 가능하게 구성하라.
테스트용 대체 경로만 확인하지 말고 실제 구현 경로를 검증하라.

테스트 자체도 간결하게 유지하라.
검증 목적에 비해 과도한 테스트 프레임워크나 복잡한 보조 코드를 만들지 마라.


6. 리소스 사용과 실행 경계

작고 빠르며 기존 환경과 데이터에 영향을 주지 않는 테스트는
별도 승인 없이 진행하라. Root AGENTS.md의 가벼운 검증 범위를 따른다.

리소스를 많이 쓰는 최종 실제 테스트·실험은 사용자가 직접 실행한다.
Agent는 이를 실행·제출·재시도·재개하지 않는다.
사용자 승인을 받아 agent가 대신 실행하는 절차로 대체하지 않는다.
전체 benchmark, 실제 학습·평가·sweep, 대형 모델 로딩,
대규모 데이터 처리·다운로드 등 무거운 준비 과정도 같은 경계에 포함한다.

무거운 검증이 필요하면 목적과 확인 가능한 자원 부담을 설명하고,
사용자가 직접 실행할 커맨드·config·실행 가이드를 준비하되 실행하지 마라.
필요한 작업 경로, 환경·사전 준비, 필수 옵션, 결과 저장 위치,
성공·실패·중단 기준과 사용자에게 돌려받을 결과를 포함하라.
리소스 요구를 측정하지 않았다면 추정 또는 미확인으로 명시하라.

작은 입력이어도 모델 로딩·fixture·초기화가 무거우면 가벼운 테스트가 아니다.
반복·병렬 실행의 총부하까지 판단하라.
부담이 불확실하면 실행하지 말고 사용자 실행 항목으로 분리하라.

구현 요청, 실험 계획의 승인, 실행 예산은 본 실험의 agent 실행 허가가 아니다.
실행 가이드를 만들었다고 실제 실행하거나 검증한 것처럼 보고하지 마라.
본 실험은 NOT_RUN으로 명시하고, 독립적으로 가능한 가벼운 검증까지만 수행하라.


7. 결과 보고

각 phase가 끝나면 핵심 변경점, 실행한 테스트와 결과,
남아 있는 문제만 간단히 보고하라.

실제로 실행한 테스트와 실행하지 못한 테스트를 명확하게 구분하라.
가벼운 테스트의 통과를 전체 품질이나 성능의 검증으로 확대 해석하지 마라.
측정하지 않은 속도 향상이나 메모리 절감 효과를 달성한 것처럼 주장하지 마라.

최종적으로 다음 내용을 짧게 정리하라.
- 구현한 내용과 주요 변경 파일
- 실제로 실행한 테스트와 결과
- 미검증 사항과 남아 있는 제약
- 테스트를 다시 실행하는 방법과, 내가 직접 실행해야 하는 추가 검증 커맨드
